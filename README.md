# Studio — виртуальная IT/геймдев команда агентов для Claude Code

Плагин `studio`: оркестратор, 5 лидов, 23 специалиста и 2 мета-агента (рекрутер и коуч).
Каждая роль — это агент со своей моделью и набором инструментов плюс скилл с базой знаний.
Команда учится на своих ошибках: каждая ошибка записывается в журнал уроков, а коуч
переносит повторяющиеся уроки в плейбуки агентов. Сильнее всего проработаны
**Unity** и **.NET**. Есть доменные модули: **iGaming/казино**, **мобильный F2P/LiveOps**,
**мультиплеер**, **PC/консоли**.

## Установка

Из GitHub (рекомендуется):
```powershell
claude plugin marketplace add FirstSymbol/Gamedev-team-claude-plugin
claude plugin install studio@studio-market --scope user
claude plugin list
```
Внутри сессии то же самое: `/plugin marketplace add FirstSymbol/Gamedev-team-claude-plugin`,
затем `/plugin install studio@studio-market`. Обновление: `claude plugin marketplace update studio-market`.

Если на Windows при добавлении маркетплейса появляется `Filename too long`, значит, путь к
папке конфигурации слишком длинный. Помогает команда `git config --global core.longpaths true`.

Из локальной копии:
```powershell
git clone https://github.com/FirstSymbol/Gamedev-team-claude-plugin.git
claude plugin marketplace add ".\Gamedev-team-claude-plugin"
claude plugin install studio@studio-market --scope user
```

После правок файлов пака перезапустите сессию или выполните `/reload-plugins`.
Чтобы попробовать пак без установки, запустите `claude --plugin-dir "<папка>\plugins\studio"`.

## Как пользоваться

| Что нужно | Как сказать |
|---|---|
| Любая задача для команды | «Команда studio, …» или просто опишите задачу: оркестратор сам выберет роли |
| Фича целиком (спека → код → тесты → ревью) | `/studio:feature ежедневный бонус с таймером` |
| Старт нового проекта | `/studio:kickoff идея: social casino с турнирами` |
| Подключить команду к уже начатому проекту | `/studio:onboard` (или `/studio:onboard docs: docs\GDD.md lessons: notes\ошибки.md`) |
| Обновить кэш проекта после больших изменений | `/studio:onboard --refresh` |
| Баг | `/studio:bugfix <описание/лог>` |
| Готовность к релизу | `/studio:release 0.4.0 Android+iOS` |
| Статус | `/studio:status` |
| Ревью рисков | `/studio:risk-review` |
| Разбор ошибок команды и обновление агентов | `/studio:retro` (или `/studio:retro unity-developer`) |
| Влить опыт проектов в пак (в папке этого репо) | `/studio:retro from D:\Projects\Casino D:\Projects\Puzzle` |
| Учесть ошибки из своего файла заметок | `/studio:retro from D:
otes\ошибки.md` (можно вместе с проектами) |
| Нужен специалист, которого нет в команде | «Команда studio, нам нужен ML-инженер для …» → `team-recruiter` |
| Конкретная роль | «Используй агента studio:economy-monetization-designer …» |

Агенты пишут результаты в папку `.team/` в корне проекта: бриф, доска задач, риски, ADR,
спеки, хэндоффы и отчёты. Между собой агенты передают пути к файлам, а не содержимое.
Это экономит токены и даёт общую «память» команды.

## Состав команды

| Группа | Роли | Модель |
|---|---|---|
| Оркестрация | orchestrator (скилл главного потока) | модель сессии |
| Лиды | producer, product-manager, tech-lead-architect, lead-game-designer, qa-lead | Opus |
| Мета-агенты | team-recruiter (создаёт новые роли), team-coach (обновляет агентов по журналу ошибок) | Opus |
| Аналитика | business-analyst, system-analyst, data-analyst | Sonnet |
| Геймдизайн | game-designer, level-designer, narrative-designer, economy-monetization-designer | Sonnet |
| Арт/UX | ux-ui-designer, art-director, technical-artist | Sonnet |
| Разработка (критичные зоны) | code-reviewer, security-engineer, multiplayer-network-engineer | Opus |
| Разработка | unity-developer, dotnet-backend-developer (effort high), frontend-developer, devops-sre-engineer | Sonnet |
| Качество/релиз | qa-engineer, release-platform-manager | Sonnet |
| Рынок/операции | marketing-manager, liveops-manager, compliance-advisor | Sonnet |
| Рутина | technical-writer | Haiku |

Почему так: ревьюер должен быть сильнее автора кода, иначе он пропускает те же ошибки.
Безопасность и неткод — зоны, где ошибка дорогая и плохо ловится тестами. Обычный код пишет
Sonnet по спекам от tech-lead на Opus. Для сложных задач (деньги, конкурентность, миграции,
повторная попытка после неудачи) оркестратор точечно запускает Sonnet-агента с `model: opus`.

Иерархия: главный поток (оркестратор) → лиды → специалисты. Агенты могут вызывать других
агентов на глубину до 3 уровней. Мелкие задачи оркестратор отдаёт сразу одному специалисту,
без лида.

Общие скиллы: `team-protocol` (правила команды, подгружается в каждого агента),
`stack-unity`, `stack-dotnet`, `domain-igaming`, `domain-f2p-liveops`,
`domain-multiplayer`, `domain-pc-console`, `unity-performance` (методика оптимизации Unity:
профилирование, A/B-замеры, перф-тесты и CI-гейты, GC/память, Burst/Jobs, IL2CPP, мобильный
нагрев; подгружается в unity-developer, technical-artist, qa-engineer).

## Существующий проект: /studio:onboard

`/studio:kickoff` рассчитан на проект с нуля: он заново придумает видение и архитектуру.
Если проект уже в работе, запустите в его папке `/studio:onboard`. Команда изучит проект и
сложит результат в `.team/` как кэш. Код при этом не меняется.

| Кто | Что делает | Результат |
|---|---|---|
| главный поток | сканеры Unity/.NET, список документов, `git log` | `.team/reports/scan-*.md` |
| tech-lead-architect | карта проекта, архитектура «как есть», ADR задним числом, техдолг | `.team/context/project-map.md`, `specs/architecture/overview.md`, `decisions/`, `risks.md` |
| qa-engineer | прогон текущих билдов и тестов: исходный уровень, «было ли зелёным до нас» | `.team/reports/baseline.md` |
| producer | что готово, в работе, дальше (по документам, git, TODO) | `.team/status.md`, `specs/plan/roadmap.md` |
| lead-game-designer или product-manager | GDD или PRD «как есть» из существующих документов | `specs/gdd/` или `specs/vision/prd.md` |
| team-coach (если указан `lessons:`) | уроки из ваших заметок об ошибках | `.team/lessons/` |

В конце команда даст короткий отчёт и список вопросов к вам. Дальше работайте как обычно:
`/studio:feature`, `/studio:bugfix` и так далее.

Как работает кэш:
- `project-map.md` — карта проекта до 150 строк: стек и версии, где что лежит, модули,
  точки входа, соглашения, команды сборки и тестов, интеграции, хрупкие места. Каждый агент
  читает её до того, как искать по коду, и не обходит проект заново. Так экономятся токены.
- `meta.md` хранит коммит, на котором собран кэш. `/studio:status` показывает, на сколько
  коммитов и файлов он отстал, и после 30 коммитов или 50 файлов пишет `STALE`.
- `/studio:onboard --refresh` обновляет только изменившиеся части по `git diff` от этого коммита.
- Если агент заметил в карте ошибку, он сообщает о ней и предлагает refresh, но сам карту
  не правит.

## Журнал ошибок: команда учится

Агенты записывают ошибки, с которыми столкнулись, и превращают каждую в правило, чтобы не
повторять её. Хранилище — markdown-таблицы, по файлу на роль:

| Где | Что |
|---|---|
| `.team/lessons/<роль>.md` | уроки этого проекта (`common.md` — для всех ролей) |
| `~/.claude/studio/lessons/<роль>.md` | глобальные уроки, работают во всех проектах |

Как это работает:
1. **Перед работой** агент запускает `lessons.py list --role <роль>` и получает до 25
   правил из проекта и глобального хранилища. Это обязательные правила на эту задачу.
2. **После работы** агент записывает урок, если упал билд или тест, ревьюер, QA или человек
   нашёл дефект, неверное допущение заблокировало работу или исправление заняло больше
   одной попытки. Ревьюер, QA и security записывают урок на роль автора кода. Повторы не
   дублируются: у существующего урока растёт счётчик `Hits`.
3. **`/studio:retro`** запускает `team-coach`. Коуч проверяет уроки по доказательствам,
   склеивает дубли и удаляет разовые. Общие уроки он переносит в глобальное хранилище, а
   повторяющиеся (`Hits ≥ 2`) и критичные (S1) — прямо в плейбуки агентов:
   - кастомные роли проекта: правит `.claude/skills/<роль>/SKILL.md`;
   - если открыт исходник этого пака: правит `plugins/studio/...` и прогоняет валидатор;
   - установленный плагин не трогает (обновление перезапишет его кэш). Вместо этого пишет
     точные правки в `.team/reports/pack-improvements.md` и поднимает урок в глобальное
     хранилище, чтобы он работал уже сейчас.

Оркестратор сам предложит `/studio:retro`, когда у роли накопится 15 и больше уроков или
появится повторяющийся S1. Пример ручного вызова скрипта:
```powershell
python "<плагин>/skills/team-protocol/scripts/lessons.py" list . --role unity-developer
python "<плагин>/skills/team-protocol/scripts/lessons.py" stats .
```

## Как залить обученную команду в git

Опыт команды лежит в нескольких местах, и всё это можно собрать в этот репозиторий:

| Что | Где копится | Как попадает в репозиторий |
|---|---|---|
| Глобальные уроки | `~/.claude/studio/lessons/` | `lessons.py export lessons` → папка `lessons/` репозитория |
| Уроки и правки к паку из проектов | `<проект>/.team/lessons/`, `.team/reports/pack-improvements.md` | `/studio:retro from <пути к проектам>` |
| Кастомные роли из проектов | `<проект>/.claude/agents/`, `.claude/skills/` | тот же retro предложит перенести их в пак |
| Свои заметки в любом формате | любой файл: md, txt, json, yaml, csv, `CLAUDE.md`, лог ревью | `/studio:retro from <путь к файлу>` |
| Плейбуки агентов | `plugins/studio/` | коуч правит их напрямую |

Порядок действий:
1. Откройте Claude Code в папке этого репозитория.
2. Запустите `/studio:retro from D:\Projects\Casino D:\Projects\Puzzle`, перечислив проекты,
   где работала команда. Коуч сделает следующее:
   - импортирует `lessons/` в глобальное хранилище;
   - соберёт уроки и `pack-improvements.md` из проектов;
   - перенесёт устоявшиеся правила в плейбуки и прогонит валидатор;
   - экспортирует вычищенные глобальные уроки обратно в `lessons/`.

   Если в проектах есть кастомные роли, retro спросит, какие из них добавить в пак, и
   перенесёт выбранные через `team-recruiter`.
3. Проверьте `git diff`, поднимите версию в `plugins/studio/.claude-plugin/plugin.json`,
   затем закоммитьте и запушьте.
4. На каждой машине выполните `claude plugin marketplace update studio-market`.

**Свои файлы не по шаблону.** В `from` можно передавать не только папки проектов, но и
отдельные файлы в любом текстовом формате. Коуч:
- читает файл, а если он больше 1500 строк, ищет места про ошибки и исправления;
- превращает каждую описанную ошибку и её решение в правило «Делай X, когда Y»;
- сам выбирает роль, критичность и теги, а в доказательство пишет `src: файл:строка`;
- отбрасывает разовые факты, секреты и личные данные;
- если роль или смысл непонятны, урок не придумывает, а пишет в отчёт.

Дальше извлечённые уроки проходят обычную чистку и попадают в плейбуки. Исходный файл не
меняется. Что взято и что отброшено, видно в `.team/reports/retro-<дата>.md`.

Перенос уроков на новую машину или коллеге (из клона репозитория):
```powershell
python plugins/studio/skills/team-protocol/scripts/lessons.py import lessons   # в глобальное хранилище
python plugins/studio/skills/team-protocol/scripts/lessons.py export lessons   # бэкап обратно в репо
```
Все правки уроков идут через скрипт: `add`, `bump`, `move --to common`, `delete --reason`,
`promote`, `export` и `import`. Руками файлы не редактируются.

Синхронизация сливает уроки по тексту правила. `Hits` берётся по максимуму и не
суммируется, поэтому повторный import или export ничего не дублирует. `export --replace`
делает папку точной копией хранилища, retro использует этот режим после чистки.
Папка `.team/` этого репозитория добавлена в `.gitignore`: рабочие отчёты retro в коммит
не попадают.

**Индекс переносов: старые уроки повторно не читаются.** Исходные проекты retro не меняет.
Вместо этого коуч отмечает каждый обработанный урок в `~/.claude/studio/lessons/_harvested.md`
(в git это `lessons/_harvested.md`): проект, роль, номер, `Hits` на момент переноса, итог
(`embedded`, `global`, `project`, `covered` или `dropped`) и ссылку на глобальное правило.

| Команда | Что делает |
|---|---|
| `lessons.py pending <проект>` | показывает только новые уроки и те, у которых вырос `Hits` (ошибка повторилась) |
| `lessons.py mark <проект> --id L-1,L-2 --outcome global --ref G-012` | записывает урок в индекс |
| `lessons.py list` в самом проекте | скрывает уроки, которые уже перенесены в пак или глобальные, чтобы агенты не читали одно правило дважды |

Проект опознаётся по адресу git-репозитория (`origin`), а если его нет, то по пути. Поэтому
после `import` индекс работает и на другой машине, если проект там тоже под git.

## Новые роли: team-recruiter

Если задаче нужен специалист, которого нет в составе, оркестратор зовёт `team-recruiter`.
Рекрутер:
1. Проверяет, нет ли уже подходящей роли. Если существующая роль покрывает потребность
   примерно на 70% или задача разовая, новую роль он не создаёт и называет подходящую.
2. Изучает предметную область и пишет агента и плейбук по стандарту `AUTHORING.md`:
   минимальные инструменты, обоснованная модель, источники, бюджеты.
3. По умолчанию кладёт роль в проект: `.claude/agents/<роль>.md` и
   `.claude/skills/<роль>/SKILL.md`, а также регистрирует её в `.team/roles.md`. Если открыт
   исходник пака, добавляет роль в сам пак вместе с ростером, оркестратором и валидатором.

Новый проектный агент подхватывается после `/agents` или перезапуска сессии. До этого
оркестратор запускает его через `general-purpose` с инструкцией прочитать файлы роли.

## Как устроена экономия токенов

1. **Постепенная подгрузка.** В контексте всегда лежат только короткие описания скиллов.
   Основной файл роли (SKILL.md) занимает не больше ~120 строк. Глубокие справочники
   (`references/*.md`) агент читает только по конкретному поводу.
2. **Командные сценарии скрыты** (`disable-model-invocation`): `/studio:feature` и другие
   не занимают место в контексте, пока вы их не вызовете.
3. **Изоляция контекста.** Каждый агент работает в своём окне и возвращает до 15 строк
   (STATUS/ARTIFACTS/…). Содержимое файлов обратно не пересылается.
4. **Модели по уровням.** Opus у лидов, мета-агентов и трёх критичных ролей (ревью,
   безопасность, неткод), у остальных исполнителей Sonnet, у рутины Haiku. Набор
   инструментов у каждой роли минимальный.
8. **Короткий журнал уроков.** `lessons.py list` выдаёт не больше 25 строк. Коуч держит
   не больше 40 уроков на роль и переносит устоявшиеся правила в плейбуки.
5. **Скрипты вместо обхода проекта.** `scan_unity_project.py` и `scan_dotnet_solution.py`
   дают сводку проекта в несколько десятков строк, вместо того чтобы агент читал сотни файлов.
6. **Английский внутри скиллов.** Токенов выходит примерно в 2–3 раза меньше, чем на
   русском. Отвечают агенты на языке пользователя.
7. **Правило «минимум ролей».** Оркестратор не зовёт роль, чей результат никому не нужен.
   Тривиальную задачу он делает сам.

Дополнительно можно скрыть описания редко используемых скиллов через `skillOverrides`
(`"name-only"`) в настройках и проверить стоимость контекста командой `/skill-doctor`.

## Режим Agent Teams (экспериментальный, по желанию)

Если специалистам нужно спорить между собой (например, GD ↔ экономист ↔ аналитик), включите
`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`. Этот режим работает только в интерактивной сессии и
дороже по токенам. Учтите, что в нём участники игнорируют поле `skills:`. Каждый агент тогда
сам вызывает свой скилл: это прописано в теле агента.

## Структура

```
.claude-plugin/marketplace.json     локальный маркетплейс
plugins/studio/
  .claude-plugin/plugin.json
  AUTHORING.md                      стандарт оформления скиллов (бюджеты, структура)
  agents/*.md                       30 агентов-ролей
  skills/<роль>/SKILL.md            плейбук роли
  skills/<роль>/references/*.md     глубокая база знаний
  skills/<роль>/templates/*.md      шаблоны артефактов
  skills/team-protocol/scripts/     сканеры проекта, статус команды и кэша, журнал уроков (lessons.py)
  skills/onboard/templates/         шаблон карты проекта (project-map.md)
lessons/                            глобальные уроки команды и индекс переносов в git (export/import)
tests/
  validate_pack.py                  проверка структуры и бюджетов
  run_triggers.py + trigger_cases.json   проверка маршрутизации (RU/EN запросы)
  sandbox/                          тестовый .NET 10 + Unity-подобный проект
```

## Тесты

```powershell
python tests/validate_pack.py --strict              # структура, бюджеты, ссылки
claude plugin validate "plugins/studio"             # официальный валидатор
python tests/run_triggers.py --jobs 4               # маршрутизация (тратит токены)
```

- Новый общий скилл `unity-performance` (6 справочников), его подгружают unity-developer,

## Как добавить роль

Проще всего попросить команду: «Команда studio, добавь в пак роль <кто> для <чего>». Сессию
нужно запускать в папке этого репозитория, тогда `team-recruiter` сам выполнит шаги ниже.
Вручную:

1. Прочитайте `plugins/studio/AUTHORING.md`.
2. Создайте `skills/<role>/SKILL.md` (+ `references/`) и `agents/<role>.md`.
3. Добавьте роль в таблицу маршрутизации `skills/orchestrator/SKILL.md`, в `ROSTER`
   в `tests/validate_pack.py` и в раздел Roster в `AUTHORING.md`.
4. Запустите `python tests/validate_pack.py --strict`.

## Ограничения

- Юридические выводы (`compliance-advisor`, `domain-igaming`) носят справочный характер.
  Решения go/no-go должен принимать юрист.
- Unity Editor агенты запустить не могут, если он не установлен или не подключён MCP.
  Компиляцию и PlayMode-проверки в этом случае нужно делать вручную или в CI (см. `stack-unity`).
- Требования сторов, консолей и законы быстро меняются. Пункты с пометкой `(verify: …)`
  нужно проверить по первоисточнику.
